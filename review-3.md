# Ревью шага 3 — кодеки значений

Критических проблем не найдено, исправлений в коде не вносилось. Проверено:

- формат на проводе соответствует §6 (`varuint(byteCount + 1)`, 0 = `null`; примитивы в полную ширину; float/double сырыми битами; ширина перечислений по §12);
- `IsChanged`: NaN == NaN, -0 == 0 (`float.Equals`/`double.Equals`), строки — ординально;
- упаковки на горячем пути нет (`Unsafe.As` в `EnumCodec`);
- типы исключений корректны;
- все тесты, требуемые планом для шага 3, присутствуют;
- сборка без новых предупреждений, 123 теста зеленые.

Ниже — некритичные замечания и риски для следующих шагов.

## Риски для следующих шагов

1. **Хэш схемы не видит изменения ширины перечисления** — `KludgeBox/Replication/Codecs/EnumCodec.cs:48`.
   Ширина компактного перечисления зависит от максимального определенного значения. Пример: на одной стороне в перечисление добавили `E = 4` после `D = 3`. Ширина меняется с 2 до 3 бит, а полное имя типа остается прежним.
   По §10 дескриптор значения в хэше — это только «value type + quantize/tolerance/manual». Рукопожатие такое расхождение не обнаружит, и поток молча рассинхронизируется.
   Рекомендация для шага 5 (`SchemaHash`): для перечислений добавлять в дескриптор `BitCount`/`IsCompact` или список определенных значений. По возможности добавлять и тип кодека (`codec.GetType().FullName`), чтобы ловить различия в пользовательских кодеках и в `StringCodec.MaxByteCount`.

2. **Сообщение исключения кодека без пути члена** — `KludgeBox/Replication/Codecs/EnumCodec.cs:67`, `KludgeBox/Replication/Codecs/StringCodec.cs:60`.
   Кодек не знает, какой член он пишет, а §13 требует путь члена в `ReplicationException`. На шаге 5 `MemberReplicator` или `ReplicationTypeModel.WriteMembers` должен перехватывать `ReplicationException` при записи и оборачивать ее с путем `DeclaringType.FullName + "." + member.Name`.

3. **`TryGet` берет блокировку при каждом вызове** — `KludgeBox/Replication/Codecs/ReplicationCodecs.cs:123`.
   Это допустимо, пока реестр используется только при построении модели, как задумано. Узлы шагов 5–8 (в частности `DictionaryNode` для ключей) должны сохранять полученный кодек в поле, а не вызывать `TryGet` на каждом кадре.

4. **Исключения ленивого создания оборачиваются в `TargetInvocationException`** — `KludgeBox/Replication/Codecs/ReplicationCodecs.cs:152`, `:173`.
   Сейчас конструкторы `EnumCodec`/`NullableCodec` при этих аргументах не бросают, поэтому это не баг. Если в конструктор кодека когда-нибудь добавят проверки, построитель модели получит `TargetInvocationException` вместо `ReplicationException`. Можно вызывать через `Invoke(obj, BindingFlags.DoNotWrapExceptions, null, args, null)`.

5. **Строковый ключ `null` в словаре** — `KludgeBox/Replication/Codecs/StringCodec.cs:91-95`.
   `StringCodec.Read` законно возвращает `null`. Для ключей `ReplicatedDictionary<string, …>` на шаге 8 `DictionaryNode` сам должен бросать `ReplicationFormatException` на `null`-ключ. Это требование плана (шаг 8), но кодек его не обеспечивает.

6. **Godot в режиме double precision** — `KludgeBox/Replication/Codecs/GodotCodecs.cs:21` и далее.
   В сборке Godot с `REAL_T_IS_DOUBLE` компоненты станут `double`, и вызовы `WriteSingle(value.X)` перестанут компилироваться. Допущение задокументировано в plan.md; его стоит упомянуть и в README на шаге 10.

## Некритичные замечания

7. **Строки с одиночными суррогатами** — `KludgeBox/Replication/Codecs/StringCodec.cs:27`, `:57`, `:76`.
   Кодировщик с заменой превращает одиночный суррогат в U+FFFD, поэтому клиент получает строку, отличную от серверной, без ошибки. `IsChanged` сравнивает исходные строки на сервере, так что лишних отправок нет. Поведение приемлемо, но его стоит отразить в XML-документации кодека.

8. **Два прохода по строке при записи** — `KludgeBox/Replication/Codecs/StringCodec.cs:57`, `:76`.
   Сначала `GetByteCount`, затем `GetBytes`. Для коротких строк можно кодировать сразу в стековый буфер. Это микрооптимизация: строка пишется только при изменении.

9. **Проверка отсутствия аллокаций покрывает только перечисления** — `KludgeUnitTests/Replication/CodecTests.cs:441`.
   `NullableCodec`, кодеки Godot и `StringCodec.Write` для коротких строк тоже не должны выделять память. Полная проверка запланирована на шаге 10, но дополнительный тест здесь был бы дешевой страховкой.

10. **`EnumCodec.Size` — `static readonly` поле, а не `Unsafe.SizeOf<TEnum>()` прямо в `switch`** — `KludgeBox/Replication/Codecs/EnumCodec.cs:18`, `:99`, `:115`.
    Tier-1 JIT сворачивает `static readonly` в константу, так что на практике разницы нет. Прямой вызов `Unsafe.SizeOf<TEnum>()` гарантирует свертку и на tier-0, и в AOT.

11. **Перечисления с базовым типом `nint`/`nuint`/`char`/`bool` (возможны только из IL)** — `KludgeBox/Replication/Codecs/EnumCodec.cs:142-146`.
    `IsSignedUnderlying` не учитывает `nint`. Такое перечисление с отрицательным значением попадет в компактный режим и затем бросит исключение при записи. Из C# такие перечисления не объявить, поэтому риск только теоретический.

12. **Хрупкий тест на канонически эквивалентные строки** — `KludgeUnitTests/Replication/CodecTests.cs:281`.
    Литералы `"é"` (U+00E9) и `"é"` (e + U+0301) различаются только нормализацией Unicode. Редактор или git-фильтр, который нормализует исходники в NFC, незаметно сделает тест неверным. Надежнее записать литералы через escape-последовательности: `"é"` и `"é"`.
