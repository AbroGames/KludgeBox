# Ревью шага 8 — `ReplicatedDictionary<TKey,TValue>`

Критических ошибок я не нашел, поэтому код не менял. Сборка проходит без новых предупреждений: остается только прежнее NU1902 про `Microsoft.Build.Tasks.Git` и старые предупреждения в `KludgeTests`. Все 349 тестов проходят.

Что проверено:
- **Формат (§6).** Бит present, бит reset. Удаления пишутся только при `!reset`. Вставки и изменения идут с битами продолжения, части с порядком нет.
- **Отправитель.**
  - `reset` выставляется при `forceAll`, при незаписанной тени и при другой ссылке.
  - Быстрый путь O(1) срабатывает только для значений без внутреннего состояния.
  - Значения-значения пишутся только при структурном изменении.
  - Пустые записи откатываются, `Commit` вызывается и при пустой структурной дельте.
- **Удаление и повторное добавление ключа в одном кадре.**
  - С тем же значением ничего не отправляется.
  - С другим значением отправляется только запись.
  - С другим объектом `ObjectNode` видит новую ссылку и пишет все члены с `forceAll`. Клиент переиспользует свой экземпляр при совпадении типа или создает новый при другом типе.
  - С новым списком или словарем отправляется reset.

  Устаревших экземпляров и членов не остается.
- **Получатель.**
  - Удаление отсутствующего ключа ничего не делает.
  - При сбросе значения под тем же ключом переиспользуются, незаписанные ключи удаляются в `EndReset` (он стоит в `finally`).
  - Повтор ключа при сбросе отвергается до чтения значения.
  - Ключ `null` отвергается без упаковки.
  - Лимиты чтения и записи согласованы.
- **Снимок** пишется только из тени.
- **Маршрутизация в построителе модели.** Ключи отбираются через `CanEncode`. Quantize/Tolerance применяются только к значениям.
- **Временные тесты**, которые не вошли в репозиторий:
  - стресс-тест, 6 × 3000 кадров. Словари объектов с вложенными словарями и списками, полиморфные значения, один объект в нескольких словарях и под несколькими ключами, обмен и алиасинг экземпляров словарей, словарь словарей. Удаление и повторное добавление ключа с тем же или другим объектом, обмен значений между ключами, `NaN` в значениях. До 6 поздних клиентов с «мусором». После каждого кадра проверялось, что повторная дельта пуста.
  - фазз-тест, 100 000 испорченных или обрезанных пакетов. Каждый раз проверялась согласованность перечисления и поиска и то, что следующий снимок восстанавливает состояние сервера.

  Расхождений не нашлось.

Ниже только то, что не исправлялось.

## Риски для следующих шагов

1. **`KludgeBox/Replication/Model/ReplicationModelBuilder.cs:159` — ключ ссылочного типа с пользовательским кодеком допускается.**
   Если у такого класса нет `Equals`/`GetHashCode` по значению, получатель при каждом чтении создает новый экземпляр ключа. Тогда удаления становятся no-op, а записи добавляют новые записи вместо изменения существующих, и клиент молча расходится с сервером. С `string` проблемы нет. Та же проблема у кодека с потерями (например, квантующего), если он отображает разные ключи сервера в один ключ клиента. Возможные меры:
   - отвергать ключи-классы, кроме `string`;
   - либо описать в README, что кодек ключа обязан быть без потерь, а тип ключа — сравниваться по значению.

2. **`KludgeBox/Replication/ReplicatedDictionary.cs:18`, `:22` — ключи-структуры без `IEquatable<T>`.**
   Сюда относятся пользовательские структуры с зарегистрированным кодеком, например `Invalid.NoCodec` из тестов. Для них `EqualityComparer<TKey>.Default` — это `ObjectEqualityComparer`, и на каждое хеширование или сравнение приходится упаковка плюс рефлексивный `ValueType.Equals`. Это касается и отправителя (`Inner`, `shadow.Entries`), и получателя (`_resetPending`). Встроенные ключи (примитивы, перечисления, `Nullable<T>`, векторы Godot) не упаковываются. Утверждение «без аллокаций» для таких ключей неверно. Это стоит упомянуть в README (шаг 10) или проверять `IEquatable<TKey>` при построении модели и выдавать предупреждение.

3. **Шаг 9: manual-член типа `ReplicatedDictionary`.**
   При `MarkDirty` запись идет в настоящую тень с `forceAll`, то есть через `WriteReset`, который переиспользует тени значений. Это корректно, но стоит покрыть тестом по аналогии с п. 5 review-7. Сценарий: manual-словарь объектов, `MarkDirty`, затем изменение члена значения без `MarkDirty`; такое изменение не должно отправляться.

4. **Шаг 10, фазз-тест и память.**
   При сбросе старые записи остаются до `EndReset`, так что словарь временно держит до 2 × `MaxCollectionCount` записей. Для вложенных словарей лимит действует на каждый словарь отдельно. Общий объем все равно ограничен размером входа (каждая новая запись стоит битов), но для фазз-теста с «большими аллокациями» полезно знать, что предел не `MaxCollectionCount`, а длина пакета.

5. **`KludgeBox/Replication/ReplicatedDictionary.cs:316` — получатель, который читает свой экземпляр словаря повторно (reentrancy).**
   Если граф клиента содержит тот же экземпляр `ReplicatedDictionary` внутри его собственного значения, вложенный `BeginReset` затрет `_resetPending` внешнего сброса. Граф, который строит репликация, так не выглядит; это возможно только при ручной инициализации полей на клиенте одним экземпляром. Для полноты стоит указать в README то же правило, что и для списков: получатель не изменяет и не разделяет реплицируемые коллекции.

## Некритичные замечания

6. **`KludgeBox/Replication/ReplicatedDictionary.cs:63`, `:68`, `:216` — публичные `Keys`, `Values` и `GetEnumerator` возвращают типы `Dictionary<,>`.**
   Это закрепляет реализацию в публичном API. Зато перечисление обходится без аллокаций, так что компромисс разумный. Но если позже понадобится другая внутренняя структура (например, сохранение порядка), это будет ломающее изменение.

7. **`KludgeBox/Replication/ReplicatedDictionary.cs:316` — `_resetPending` сохраняет емкость после сброса.**
   Если словарь был большим, память под `HashSet` остается до сборки мусора самого словаря. Это мелочь; можно вызывать `TrimExcess`, когда множество заметно больше словаря.

8. **Публичный API беднее `Dictionary<,>`.**
   Нет `EnsureCapacity`, `TrimExcess`, `Comparer`, `GetValueOrDefault` (последний доступен как расширение через `IReadOnlyDictionary`). План требует только перечисленное в §7. Каждая новая мутирующая операция обязана увеличивать `_version`.

9. **`KludgeBox/Replication/Nodes/DictionaryNode.cs:62` — свойство называется `ItemNode`, хотя поле называется `_valueNode`.**
   Имя, видимо, выбрано для единообразия с `ListNode`, но в словаре это узел значений. Это косметика.

10. **Тесты (`KludgeUnitTests/Replication/ReplicatedDictionaryTests.cs`).**
    - Нет отдельного теста на удаление ключа и повторное добавление с **другим экземпляром объекта** в одном кадре. На проводе это то же, что замена через индексатор (`:787`), и рандомизированный тест такое покрывает, но явной проверки `Assert.Same` для этого случая нет.
    - Нет теста на ключ-класс с зарегистрированным кодеком (см. п. 1).
    - В рандомизированном тесте (`:1384`) значения-объекты никогда не содержат вложенных словарей или списков, и нет словаря словарей. Мой временный стресс-тест покрывал это и расхождений не нашел, но постоянного теста нет. Шаг 10 все равно добавит сквозной рандомизированный тест, и такие модели стоит включить туда.
    - `Malformed_DuplicateKeyInResetThrows` проверяет согласованность только для второго случая и только через перечисление. Проверки `Count` против числа перечисленных записей нет.
