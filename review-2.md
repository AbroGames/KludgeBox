# Ревью шага 2 — неисправленные замечания

Ниже только некритичные замечания, предложения и риски для следующих шагов. Исправленное здесь не перечисляется.

1. **KludgeBox/Reflection/Access/TypedAccessors.cs:207 (`ConvertIfNeeded`)** — `Expression.Convert` разрешает любые явные преобразования: сужающие числовые (`TValue = long` для поля `int` молча обрежет значение в сеттере), пользовательские `explicit operator`, упаковку (`TValue = object` для члена-структуры). Для универсального хелпера это задокументировано и допустимо. Риск для шага 5: `ReplicationModelBuilder` обязан создавать `MemberReplicator<TOwner,TValue>` с `TValue`, **точно равным** типу члена (через `MakeGenericMethod`), иначе в горячем пути появится упаковка или скрытое преобразование. Стоит добавить в билдере assert `typeof(TValue) == memberType`.

2. **TypedAccessors.cs:196 (`ConvertOwner`)** — если `TOwner` — базовый тип (например, `object`), в делегат вшивается `castclass`/`unbox`. Передача владельца неверного типа даст `InvalidCastException` в момент вызова, а не при создании. Для репликации это нормально (шаг 5 будет использовать точный тип владельца), но при использовании `object` каждое обращение платит за проверку типа. Рекомендация для шага 5: создавать аксессоры с `TOwner` = объявляющий тип или тип модели.

3. **TypedAccessors.cs:62, 114** — перехватываются только `InvalidOperationException` и `ArgumentException`. Экзотические члены (ref-возвращающие свойства, поля указателей, byref-like типы) могут выбросить `NotSupportedException` и т. п. без пути члена в сообщении. Для репликации такие члены всё равно должен отвергать билдер (шаг 5) по типу члена, до вызова `TypedAccessors`.

4. **TypedAccessors.cs:215 (`IsStatic`)** — определение статичности по первому найденному аксессору. Для корректного C# это всегда верно; замечание только для полноты.

5. **KludgeBox/Core/ITypeIdMapping.cs:15, 23** — контракт исключений: неизвестный тип или id — `KeyNotFoundException` (так ведёт себя `TypesMappingService`). Риск для шага 6: `ObjectNode` обязан перехватывать это исключение и превращать его в `ReplicationException` при записи (подтип без отображения) и в `ReplicationFormatException` при чтении (неизвестный id). Иначе фазз-тест шага 10 («единственный допустимый тип исключения — `ReplicationFormatException`») упадёт. Альтернатива — добавить `TryGetType`/`TryGetId`, но это изменение интерфейса относительно плана.

6. **ITypeIdMapping.cs:24** — метод `GetType(int)` перегружает `object.GetType()`. Вызов `mapping.GetType()` без аргумента молча вернёт тип реализации, а не ошибку. Это требование плана (§12, шаг 2), поэтому не менялось; при желании можно переименовать (например, `GetTypeById`) до того, как на интерфейс завязался шаг 6.

7. **KludgeBox/Core/TypesMappingService.cs:18–33** (существующий код, не изменён) — `AddTypes` не очищает словари: повторный вызов с меньшим списком оставит устаревшие id, а id зависят от сортировки по `FullName` только в пределах переданного списка. Для полиморфной репликации отображение должно совпадать у сервера и клиента; это стоит отметить в README (шаг 10).

8. **KludgeUnitTests/Reflection/TypedAccessorsTests.cs** (`StaticField_IgnoresOwner`) — тест меняет глобальное статическое состояние `Holder.StaticField`. Сейчас его больше никто не читает, но при добавлении тестов на это поле возможны гонки при параллельном запуске xUnit.

9. **TypedAccessorsTests.cs** — нет тестов на `TOwner` — интерфейс, реализуемый объявляющим типом, и на `Nullable<T>`-преобразования (`TValue = int?` для поля `int`). Код их поддерживает; тесты не обязательны по плану.

10. **Риск для шага 5 (обход членов):** приватные поля базового типа не видны через `typeof(Derived).GetField(...)` вообще, поэтому билдер должен обходить иерархию с `DeclaredOnly` на каждом уровне, как описано в §10. Для свойств `TypedAccessors` теперь сам нормализует `PropertyInfo`, полученный через наследника.
